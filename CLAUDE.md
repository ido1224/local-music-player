Project: Local Music Player (Android) — Phase 1
Overview
Native Android app (Kotlin) for local, offline music playback with a custom library and manual playlists. This is Phase 1 of a larger project — later phases add listening tracking, on-device AI recommendations, and a NERA-backed "Discover" feature. Do not build those yet. Phase 1 is playback + library only, but the schema and structure should be clean enough to extend later (see "Forward compatibility" below).
Goals for this phase

1. A working Android app that plays audio files stored in its own app-managed music folder (not full-device auto-scan).
2. A file import flow: user picks files via Android's Storage Access Framework, app copies/references them into its library and reads ID3/tag metadata (title, artist, album, genre, year, duration).
3. Standard playback controls: play/pause/skip/seek/shuffle/repeat, a visible queue.
4. Background playback with lock-screen and notification media controls.
5. Manual, user-created playlists (create/rename/delete, add/remove tracks, reorder).

Tech stack

* Language: Kotlin
* Min SDK: 26 (Android 8.0) — confirmed
* Package name: com.nera.musicplayer
* App name: Nera Music (display name only — changed 2026-08-29 from "NERA Music Player"; package name `com.nera.musicplayer` deliberately left as-is to avoid a reinstall)
* Playback: ExoPlayer (Media3) via `androidx.media3`
* Background/notification controls: `MediaSessionService` (Media3)
* Database: Room (SQLite) — for tracks, playlists, playlist_tracks
* File import: Storage Access Framework (`ACTION_OPEN_DOCUMENT`, persistable URI permissions) — do NOT request broad `MANAGE_EXTERNAL_STORAGE`
* Metadata extraction: Media3's built-in metadata retriever, or `androidx.media3.exoplayer.MetadataRetriever` — avoid adding a second tag library unless it proves necessary
* UI: Jetpack Compose (Material 3)
* Architecture: MVVM — ViewModel + Repository pattern, Room as single source of truth, StateFlow for UI state

Data model (Room) — design for extension
Even though Phase 1 only needs playback + playlists, structure these tables now so Phase 2/3 (listening history, feature vectors) can be added without migration pain:

* `Track`: id, uri, title, artist, album, genre, year, durationMs, dateAdded, fileSizeBytes
   * Leave room conceptually for a future `feature_vector` table (one-to-one with Track) — don't build it now, just don't name things in a way that collides with it later.
* `Playlist`: id, name, dateCreated, dateModified
* `PlaylistTrack`: playlistId, trackId, position (join table, ordered)

Do NOT add listening-history or feature-vector tables yet — that's Phase 2/3.
File organization
Use a standard modern Android project layout:

```
app/src/main/java/<package>/
  data/          — Room entities, DAOs, database class, repository
  playback/      — ExoPlayer wrapper, MediaSessionService, playback state
  ui/            — Compose screens (Library, Player, Playlists, Import)
  ui/theme/      — Compose theming

```

Explicitly out of scope for this phase

* Listening tracking / history logging
* Audio feature extraction (tempo, energy, etc.)
* Any AI/similarity/recommendation logic
* NERA/Ollama networking or sync
* Discover menu
* Home screen widget
* Android Auto
* Equalizer

If you find yourself writing code for any of the above, stop — that's a later phase.

- Follow-up, same spike (2026-08-29): added `click_track_120bpm.wav` — a synthetic asset generated specifically for this test (`app/src/androidTest/assets/`, not reused from playback milestones), 16 short broadband noise-burst "clicks" (~15ms, fast attack/exponential decay) exactly every 500ms = 120 BPM ground truth, 8s total. `TarsosDspSpikeTest` refactored: `runOnsetDetection(assetName)` extracted as a shared helper, two `@Test` methods (sine tone, click track), and `logTempoEstimate()` compares against a known-good BPM when one exists, logging a `MATCH`/`MISMATCH` verdict (±5% tolerance) — deliberately not a hard JUnit assertion, so a tuning miss doesn't read as "library integration broke."
  - **First attempt returned 0 onsets on the click track too** — surprising, since real percussive content should trigger the detector. Diagnosed by re-reading `PercussionOnsetDetector.process()` (already fetched from GitHub for the constructor signature): it guards `if (priorMagnitudes[i] > 0.f)` before counting a bin as "over threshold" — a bin whose *previous* frame had exactly zero energy is skipped entirely. My first click track had true digital silence (sample value `0`) between clicks, so most frames immediately preceding a click had `currentMagnitudes` (and thus the next frame's `priorMagnitudes`) at exactly `0.0f`, silently defeating the diff-based detector. This is a real property of the algorithm — it assumes a nonzero noise floor, which real-world recordings always have and pure synthetic silence doesn't.
  - **Fix**: regenerated the click track with a small dither noise floor (±40 out of 32767, inaudible) between clicks, so no bin is ever exactly zero-energy. This is a correction to an unrealistic property of the *test asset*, not tuning the library to force an answer.
  - **Result after the fix**: 4 onsets detected (not 16) at `[4.04s, 5.04s, 6.04s, 7.04s]` — evenly spaced exactly 1.0s apart, i.e. **every other click**, starting only at click #9 of 16. Computed tempo: **60.1 BPM vs. 120 BPM ground truth (49.9% error, MISMATCH)**. This is a textbook **octave error** (locking onto half the true tempo) — a known failure mode in beat-tracking algorithms in general, not random garbage: the detector found something real and periodic, just at the wrong rate, and undercounted rather than overcounted or produced noise.
  - **Working theory** (not verified further, per instructions to stop and report): `PercussionOnsetDetector`'s defaults (`DEFAULT_SENSITIVITY = 20`, `DEFAULT_THRESHOLD = 8`) require over 80% of all 512 frequency bins to jump >8dB within a single frame to register a peak — a strict bar. With `bufferOverlap = 0`, a 15ms click can land across a 1024-sample (~23ms) frame boundary and split its energy across two frames, sometimes failing to clear that bar; per-click random noise variance plausibly pushes alternating clicks above/below the threshold.
  - **Net finding, updated**: TarsosDSP's `core` artifact is confirmed to build, link, and run cleanly end-to-end on real PCM audio, and its onset detector does find real periodic percussive events (not noise) — but **the default `PercussionOnsetDetector` configuration is not usable as-is** for reliable tempo detection; it undercounted by exactly half on a clean, unambiguous 120 BPM click track.

## Pipeline design: tempo analysis at import time (2026-08-29, done and verified)

Per explicit user direction: run the validated `ComplexOnsetDetector` → `BeatRootOnsetEventHandler` pipeline once per track at import time (not per-play), cache the result in Room alongside `Track`.

- **TarsosDSP promoted from androidTest-only to a real app dependency** (`implementation(libs.tarsosdsp.core)` in `app/build.gradle.kts`, alongside the existing `androidTestImplementation` used by the spike). The spike test (`TarsosDspSpikeTest`) and its assets are left in place as regression coverage / documentation of the validation trail — not deleted now that the pipeline is real.
- **`data/TrackAudioFeatures.kt`**: one-to-one with `Track` (`trackId` is both PK and FK, `onDelete = CASCADE` — matches the pattern already used for `ListenEvent`/`PlaylistTrack`). Fields: `bpm: Float?`, `analyzedAt: Long`. Deliberately minimal — just what's needed now, not a speculative full feature-vector row (CLAUDE.md's original Phase 1 note about leaving room for a future `feature_vector` table still applies to anything beyond bpm). `TrackAudioFeaturesDao` has `upsert` (REPLACE on conflict, since re-analysis should overwrite) and `getForTrack`. `AppDatabase` bumped to version 3 (still `fallbackToDestructiveMigration()` — no real user data to preserve yet).
- **`analysis/AudioDecoder.kt`** (new package): decodes an arbitrary audio file — whatever format Android's platform `MediaCodec` supports (MP3, AAC, FLAC, WAV, OGG, ...), not just WAV like the spike's test assets — to mono 16-bit PCM via `MediaExtractor` + `MediaCodec`. Real imported files can be any format Media3 can play, unlike the spike's synthetic/extracted WAV fixtures. Downmixes multi-channel audio to mono by averaging channels (the validated spike pipeline was mono-only; stereo interleaved samples fed directly to TarsosDSP would be misread as alternating-channel noise). Seeks past the first 20s of the track before decoding (skipped if the track is too short for that to make sense) to avoid analyzing a likely quiet/silent intro, and caps decoding at 20s of source audio regardless of track length, so analysis time stays bounded independent of track duration.
- **`analysis/TempoAnalyzer.kt`**: the exact validated pipeline from `TarsosDspSpikeTest`, extracted so both the test and the real repository call the same code — `ComplexOnsetDetector(bufferSize=1024)` feeding `BeatRootOnsetEventHandler`, `dispatcher.run()`, then `trackBeats()`, then median inter-beat-interval → BPM. Returns `null` if fewer than 2 beats were found (e.g. silence, or analysis genuinely failed to find anything) rather than a bogus number.
- **`data/MusicRepository.kt`**: `importTracks()` now calls `analyzeTempo(trackId, destFile)` right after inserting each `Track` (using the Room-generated `trackId`, not re-querying). ## Energy extraction fix: multi-window sampling (2026-08-29, done and verified)

- **`AudioDecoder`** refactored: the old `decodeMonoPcm16()` (single continuous window, skip-intro heuristic) is preserved as-is for tempo — BeatRoot's induction needs one uninterrupted onset timeline; three disjoint snippets would fragment that and likely break tempo detection, so tempo's decode strategy was deliberately left untouched. Added `decodeWindowAt(filePath, startMs, maxDurationMs)` (decode a short window at an explicit caller-chosen position, no heuristic) and `getDurationMs(filePath)` (cheap duration lookup via `MediaExtractor`'s track format, no decode) as the new primitives energy needed. No longer takes a shared `DecodedAudio` — tempo and energy now decode independently, since they need fundamentally different windowing (this was the point: they can no longer share one decode pass, unlike the original design).

## AI-generated playlists v1: k-means on BPM + energy (2026-08-29, backend done and verified — UI not touched yet, per instructions)

- **`similarity/ClusterEngine.kt`** (new, pure Kotlin, same testing approach as `SimilarityEngine`): Lloyd's k-means, reusing `SimilarityEngine`'s octave-aware BPM distance and plain energy distance (exposed as `internal` for this reuse) for cluster assignment. Two design points worth remembering:
  - **Centroid seeding is deterministic farthest-point sampling**, not random or evenly-spaced-by-sort. An earlier evenly-spaced-along-sorted-combined-score attempt failed its own test: with the library's near-duplicate track pairs sitting adjacent in sort order, two of the five seeds landed on JPB-High's two near-identical copies, starving Make Me Move/On & On of a centroid and merging them into one messy 4-member cluster instead of two clean pairs. Farthest-point seeding (each new seed is the candidate farthest from every seed chosen so far) fixed it immediately — caught by `ClusterEngineTest` before this ever reached a device.
  - **Octave-aware centroid averaging**: when recomputing a cluster's centroid BPM, each member's raw BPM is first folded to whichever octave (as-is/doubled/halved) sits closest to the *current* centroid before averaging — otherwise a cluster containing both a track and its octave-ambiguous double/half-time counterpart would average toward a meaningless midpoint tempo that matches neither.

## Two bugs found during visual-polish re-verification, fixed (2026-08-29, done and verified on-device)

- **UUID showing as a track title.** Root cause: `PlaylistGeneratorVerificationTest`'s `@Before` reconstructs the library from the raw `.mp3` files already sitting in `filesDir/music/` by calling `MusicRepository.importTracks(Uri.fromFile(file))`. `importTracks`'s display-name fallback chain is `DocumentFile.fromSingleUri(context, sourceUri)?.name ?: sourceUri.lastPathSegment ?: "track"` - `DocumentFile.fromSingleUri` only resolves real SAF `content://` document URIs, so for a `file://` URI it returns null, falling through to `lastPathSegment` - which for one of our own copies is the UUID filename Room never meant to surface. That collided with one specific track (the Sky High copy) that also has no embedded ID3 title tag to fall back to first, so the raw UUID string reached the UI as the title.
  - **Fix, in production code, not just the test**: added a `UUID_FILENAME_REGEX` guard in `MusicRepository.importTracks` - if the derived fallback name is UUID-shaped, it's discarded in favor of a final `"Unknown Track"` fallback rather than trusting it as a real name. Fixed at this layer (not by patching the test helper) since any caller feeding a URI whose display name can't be resolved should get the same protection, not just this one androidTest path.
  - Existing bad row (already inserted before this fix shipped) doesn't self-heal from a code change alone, since the reconstruction only runs when the library is empty - corrected it directly via a DB pull/patch/push (`nera_music.db`, WAL checkpointed and folded in first) rather than wiping and losing the other four real tracks.
  - **Verified on-device**: fresh screenshot of the Home library list shows "Unknown Track" in place of the old UUID string, everything else (titles, BPM/Energy badges) unaffected.
- **Playlist Detail top bar overcrowding.** Root cause: the top bar packed a title plus up to four actions as literal `TextButton`s (`Back`, conditionally `Promote to manual`, `Rename`, `Delete`) plus an `IconButton` - all inline, no wrapping, so a long playlist name plus "Promote to manual" text visibly crowded/overlapped on real screen widths. This was a real layout defect, not just a style mismatch with the rest of the app.
  - **Fix**: converted the leading action to a proper icon `IconButton` (`Icons.AutoMirrored.Filled.ArrowBack`) matching the nav-icon idiom used everywhere else in the app, kept "Add tracks" as a direct `IconButton` since it's the most common action, and moved the other three (conditionally-shown "Promote to manual", "Rename", "Delete") into a `DropdownMenu` behind a `MoreVert` overflow icon - the same overflow-menu idiom `HomeScreen`'s `TrackRow` already uses for its long-press track menu, so this isn't a new pattern for the codebase. The title `Text` now has room to render in full even for long AI-generated names like "Moderate Energy / Slow" without crowding the icons.
  - **Verified on-device**: screenshotted the detail screen for `Moderate Energy / Slow` (one of the longer AI-generated names) - title renders fully, back arrow / add / overflow icons are cleanly spaced with no overlap. Opened the overflow menu and confirmed all three actions render correctly ("Promote to manual" present since this playlist is AI-generated). No crashes.
